# Attestation design

How Morrow turns NEAR AI Cloud's attestation into a guarantee the user can check. Code: `src/lib/near/client.ts`, `src/lib/near/receipt.ts`, `scripts/verify-receipt.mjs`.

## Policy

Morrow sends document text or questions to a model only if **all** of these hold. Each is enforced in code and fails closed.

| # | Requirement | Enforced by |
| --- | --- | --- |
| 1 | Gateway TDX quote is genuine; TCB status acceptable; not in debug mode | SDK `verifyGatewayAttestation` (DCAP) |
| 2 | The quote binds a nonce generated by this process for this verification | SDK nonce generation + binding check |
| 3 | The quote binds the gateway's signing key | SDK |
| 4 | Event log replays to RTMR3; configuration hash matches MRCONFIGID | SDK |
| 5 | The TLS key of the live connection is the one in the quote, and later requests are pinned to it | SDK Node client + `createPinnedTlsFetch`; Morrow's `assertPolicy` rejects an unbound gateway |
| 6 | At least one NEAR model report exists for the model, and every returned report verifies (TDX, nonce, signer, GPU evidence when present) | SDK `verifyModelAttestation`; Morrow's `assertPolicy` rejects zero reports |
| 7 | Chat only: content is encrypted to the model key bound in a verified quote | SDK `e2ee: true` |
| 8 | Chat only: the response signature verifies over the exact bytes and its signer matches the verified evidence | SDK `verifyResponse`; on failure `chat()` throws and the answer is never stored or shown |

There is no configuration switch that disables these checks and no alternative provider.

## Sequence for one question

```
ask(question)
 ├─ search()
 │   ├─ keyword search                         local, nothing sent
 │   ├─ verify(embedding model)                fresh nonce unless verified < 10 min ago
 │   ├─ POST /embeddings                       TLS pinned to the attested gateway key
 │   ├─ verify(rerank model)
 │   └─ POST /rerank                           TLS pinned
 ├─ no passages found?  → return "no sources", no model call
 ├─ verify(chat model)
 ├─ chat.completions.create                    E2EE to attested model key, non-streamed
 ├─ verifyResponse(completion id)              signature over request/response hashes, signer == attested signer
 ├─ validate citations against supplied passages
 └─ store answer + verification summary + receipt file
```

## Freshness and replay

- The nonce is 32 random bytes generated by the SDK inside Morrow's process for each verification; it is never accepted from the network.
- A verified session is reused for at most `MORROW_ATTESTATION_TTL_MINUTES` (default 10; the SDK default is 60). The Privacy Center's "Run a fresh verification" always uses a new client with caching disabled.
- Tests (`npm run test:live`): two consecutive verifications carry different nonces; a genuine report checked against a different nonce is rejected (`binding.nonce_mismatch`); a report with a swapped signer is rejected; a quote with one flipped hex digit is rejected.

## What the user sees

- **Per answer:** a panel listing the seven checks that ran, the enclaves used for embedding, reranking and answering with their nonces and TCB status, the response signer, the gateway signer and TLS key, the request and response hashes, and the completion id.
- **Privacy Center:** on-demand verification of all three enclaves with timing and evidence.
- The panel appears only when verification succeeded, because an unverified answer is never produced. Wording distinguishes a model-enclave signature from a gateway signature.

## Receipts and independent verification

For every answer Morrow writes `data/receipts/<user hash>-<answer id>.json` containing the raw gateway report, the matching model report(s), the nonces, the TLS fingerprint and the signature. It contains no question, document text or answer.

`node scripts/verify-receipt.mjs <file>` re-runs, with no access to Morrow and no API key:

1. signature validity over the signed text (EIP-191 for `ecdsa`, raw Ed25519 otherwise);
2. full gateway attestation verification from the stored report against the stored nonce and TLS key;
3. full model attestation verification for each stored report;
4. that the response signer equals the signer bound into the verified quote.

Checked on 2026-11-14 with real evidence: genuine reports pass steps 2 and 3; a receipt whose signature was made with an unrelated key fails step 4; a receipt with an altered nonce fails step 2. (A receipt from a real completion has not been produced yet; see BLOCKERS.md.)

## Honest limits

- The receipt proves a verified enclave for this model signed text committing to two hashes. Morrow checked those hashes against the real bytes at answer time; the bytes are not retained, so a third party cannot re-derive them from the receipt.
- Intel collateral and NVIDIA evidence change over time; a receipt that verifies today may report a different TCB status later.
- Embedding and rerank responses are not signed. Their protection is "sent only to an attested gateway over a pinned TLS key, for a model whose enclave was verified".
- Morrow does not pin enclave measurements to known-good source builds (image provenance). It trusts any genuine TDX enclave that the NEAR AI gateway presents for the requested model.
- None of this covers the Morrow server itself.
